*최종 수정: 2026-05-23*

## 1. A/B 테스트 전략 개요

### 1.1 원칙

- **데이터 우선:** 베이스라인 데이터 확보 후 테스트 시작 (최소 2주)
- **한 번에 하나:** 동시에 여러 변수 테스트 금지 (인과관계 파악 불가)
- **가설 기반:** 모든 테스트는 명확한 가설과 기대 효과를 가져야 함
- **통계적 유의성:** 95% 신뢰수준 (p < 0.05) 달성 후 결론
- **최소 샘플:** 페이지당 1,000 방문 이상에서만 테스트

### 1.2 테스트 우선순위 기준

```
우선순위 점수 = (예상 임팩트 × 확신도) / 구현 난이도

예상 임팩트: 1-5 (전환율 개선 기대치)
확신도: 1-5 (가설의 근거 강도)
구현 난이도: 1-5 (구현 시간, 5=가장 어려움)
```

### 1.3 테스트 타임라인

```
Phase 1 (런치 후 2-4주): 베이스라인 수집
Phase 2 (4-8주): 히어로/CTA 테스트
Phase 3 (8-12주): 가격/온보딩 테스트
Phase 4 (12-16주): 페이지/콘텐츠 테스트
```

## 5. 테스트 실행 프로세스

### 5.1 단일 테스트 워크플로우

```
1. 가설 작성 (1일)
   - "X를 Y로 변경하면 Z 지표가 N% 개선될 것이다"

2. 구현 (1-3일)
   - A/B 변형 구현
   - 이벤트 추적 확인
   - QA 검증

3. 트래픽 할당 (즉시)
   - 50/50 분할 (동일 트래픽)
   - 최소 1,000 방문/변형까지 대기

4. 데이터 수집 (2-4주)
   - 중간 확인만 (조기 중단 금지)
   - 일일 데이터 품질 확인

5. 결과 분석 (1일)
   - 통계적 유의성 확인
   - 1차 + 2차 지표 분석
   - 부작용 확인

6. 의사결정 (1일)
   - 승리 변형 적용 또는
   - 추가 테스트 또는
   - 불확정 (데이터 부족)
```

### 5.2 테스트 규칙

- **동시 테스트:** 최대 1개 (트래픽이 충분하지 않음)
- **최소 기간:** 2주 (요일 효과 제거)
- **최대 기간:** 4주 (시간 낭비 방지)
- **조기 중단:** 부정적 결과가 -20% 이상일 때만
- **결과 공유:** 모든 테스트 결과를 문서화 (성공/실패 무관)

### 5.3 필요 트래픽 계산

```
현재 전환율: C (베이스라인 측정 후)
최소 감지 가능 효과: MDE (목표 개선율)
통계적 검정력: 80%
유의수준: 5%

필요 샘플/변형 ≈ (16 × C × (1-C)) / MDE²

예시:
  C = 5% (CTA 클릭률), MDE = 20% (상대 개선)
  필요 샘플/변형 ≈ (16 × 0.05 × 0.95) / 0.01²
                    ≈ 7,600 방문/변형
  총 필요: 15,200 방문

  일일 200 방문 시: 76일 (약 11주)
  → MDE를 30%로 조정 시: 약 5주
```

**현실적 접근:**
- 초기 트래픽이 낮으므로 큰 개선(30-50%)만 감지 가능
- 통계적 엄격함보다 방향성 확인에 집중
- 트래픽이 증가하면 더 미세한 개선도 테스트 가능

## 6. 측정 인프라

### 6.1 이벤트 추적 요구사항

모든 A/B 테스트를 위해 다음이 필요:

```typescript
// analytics_events에 variant 필드 추가
interface AnalyticsEvent {
  id: string;
  user_id: string | null;
  anonymous_id: string | null;
  event_name: string;
  properties: JSONB;  // 여기에 test_id, variant 포함
  path: string | null;
  referrer: string | null;
  utm_source: string | null;
  utm_medium: string | null;
  utm_campaign: string | null;
  created_at: string;
}
```

### 6.2 테스트 할당 로직

```
1. 사용자가 페이지 방문
2. 익명 ID 기반으로 해시 → 50/50 분할
3. variant를 cookie에 저장 (일관성 유지)
4. 모든 이벤트에 test_id + variant 기록
5. 분석 시 variant별로 그룹핑
```

### 6.3 결과 분석 쿼리

```sql
-- 테스트 결과 분석
SELECT
  properties->>'test_id' AS test_id,
  properties->>'variant' AS variant,
  COUNT(DISTINCT CASE WHEN event_name = 'home_viewed' THEN anonymous_id END) AS visitors,
  COUNT(DISTINCT CASE WHEN event_name = 'cta_clicked' THEN anonymous_id END) AS clicks,
  ROUND(
    COUNT(DISTINCT CASE WHEN event_name = 'cta_clicked' THEN anonymous_id END)::numeric /
    NULLIF(COUNT(DISTINCT CASE WHEN event_name = 'home_viewed' THEN anonymous_id END), 0) * 100,
    2
  ) AS ctr_pct
FROM analytics_events
WHERE properties->>'test_id' = 'test_001'
  AND created_at >= '2026-06-01'
GROUP BY 1, 2
ORDER BY 2;
```

## 9. 요약

**A/B 테스트 로드맵의 핵심:**

1. **베이스라인 먼저:** 2주간 데이터 수집 후 테스트 시작
2. **높은 임팩트 먼저:** 히어로, CTA, 한도 메시지 순서
3. **한 번에 하나:** 동시 테스트 금지
4. **문서화:** 모든 결과를 기록하여 학습 축적
5. **현실적 기대:** 초기에는 큰 개선(30%+)만 감지 가능

**성공 기준:**
- 런치 후 6개월 내 8개 이상 테스트 완료
- 3개 이상의 검증된 개선안 적용
- CTA 클릭률 베이스라인 대비 30% 이상 개선
